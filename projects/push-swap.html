Case study / Algorithms

Sorting integers through two constrained stacks

Push Swap is a C program that validates integers, represents them as linked-list stacks, and prints a legal sequence of stack operations that places the values in ascending order.

Role
Algorithm design and C development
Stack
C, linked lists, Make
Focus
Ranking and operation planning

Overview

Sort by describing every allowed move

The program receives integers and may only manipulate two stacks with a fixed operation set: swap, push, rotate, and reverse rotate, including combined variants. It does not print the sorted values; it prints the instructions that produce the sorted state.

A separate checker executable reads those instructions, applies them to the same input, and reports whether stack A is sorted and stack B is empty. This separates operation generation from result verification.

Problem and goals

Plan a short legal route through a restricted operation set

A general sorting algorithm cannot move values arbitrarily here. Every change must be expressed through valid operations on the top or ends of two stacks, so data representation and movement strategy directly affect the generated instruction sequence.

  • Reject malformed, duplicate, and out-of-range integer input.
  • Handle one quoted argument as well as separate arguments.
  • Represent both stacks with reusable linked-list operations.
  • Use dedicated paths for already sorted and very small inputs.
  • Choose larger-input moves from relative ranks rather than values.
  • Verify generated instructions independently with the checker.

Implementation

Normalize first, then plan stack movement

Validate before allocating the complete stack

Input checks reject unsupported characters and duplicate values. Conversion uses a long accumulator and reports values outside the signed 32-bit integer range before returning an int.

Store value and rank in each linked-list node

Each stack node keeps the original integer, a relative rank, and a pointer to the next node. Stack operations can relink nodes or change the ordering without needing a fixed-size array.

Replace value magnitude with relative order

Rank initialization repeatedly identifies the lowest unranked value. After ranking, a large negative number and a large positive number can be compared through compact positions from smallest to largest.

Use explicit small-input strategies

Empty and already sorted inputs stop early. Two values use a swap when needed, while three values use a dedicated decision path. This avoids applying the larger chunk strategy where direct moves are easier to reason about.

Distribute larger inputs through rank chunks

The main path calculates a chunk count and rank boundaries from the input size. Values in the active range move from stack A to stack B, with rotations used to position candidates and organize the moved ranks for the rebuilding stage.

Rebuild stack A from ranked candidates

After the remaining small part of stack A is sorted, the algorithm identifies high-ranked candidates in stack B, chooses rotations, pushes values back to A, and performs a final rotation when needed.

Validation and verification

Keep bad input and bad moves observable

Validation covers character format, duplicate integers, and signed 32-bit overflow. Allocated argument arrays and stack nodes have dedicated cleanup functions, including the single quoted-argument path created by ft_split.

The checker accepts only the eleven supported instruction names. An unknown instruction reports an error; a complete sequence reports OK only when stack A is sorted and stack B is empty, otherwise it reports KO.

Testing

Verify the result, not just the generator

Both executables compile with -Wall -Wextra -Werror. A current source check built push_swap and checker, piped a generated sequence into the checker, and received OK for an unsorted five-value input.

  • Confirm sorted input generates no unnecessary instructions.
  • Test duplicate, malformed, empty, and overflowing input.
  • Run two- and three-value permutations through the checker.
  • Pipe larger deterministic samples into the checker.
  • Reject unknown checker instructions instead of ignoring them.
  • Review operation counts without calling the strategy optimal.

The verified sample demonstrates correctness for that path, not a universal performance result. This case study therefore describes the implemented strategy without inventing benchmark numbers or an optimality claim.

Outcome

What the project made concrete

Push Swap turned algorithm quality into a visible stream of legal operations. It required each planning decision to work with the data structure rather than assuming random access to any value.

  • Normalization can simplify decisions without losing ordering.
  • Small cases deserve direct, testable algorithms.
  • Linked-list structure shapes the cost of every movement.
  • An independent checker creates a stronger correctness boundary.
  • Input validation is part of the algorithm's public contract.
  • Performance claims require measurements, not intuition.
