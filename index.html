Case study / Frontend

Building a portfolio by learning the browser platform

This portfolio began as a first complete web project and grew into a responsive, accessible interface built without a framework or runtime dependency.

Role
Design and development
Stack
HTML, CSS, JavaScript
Focus
Accessibility and responsive design

Summary

A real project for learning fundamentals

The site presents frontend and Unix systems work in a compact bento layout. HTML owns the content, CSS owns the visual system, and JavaScript adds focused behavior for sections, themes, filters, clocks, forms, and reveals.

Problem

Turn separate lessons into one maintainable website

Learning isolated tags and properties did not explain how a whole interface fits together. The portfolio needed to connect those lessons without hiding them behind a framework.

Implementation decisions

Browser-native structure first

  • Semantic sections and one page-level heading keep structure clear.
  • CSS Grid controls the page shell and project gallery.
  • Custom properties keep dark, light, and accent themes centralized.
  • JavaScript features are guarded so optional missing markup does not break the page.
  • The contact form prepares an email draft instead of pretending to send server data.

Accessibility and testing

Enhanced behavior stays optional

The build keeps visible focus states, linked form labels and errors, reduced-motion handling, and no-dependency Node checks. Browser checks cover responsive layout, theme persistence, filtering, form states, and section switching.

Outcome and lessons

Readable code matters as much as polish

The implementation made the boundaries between HTML, CSS, and JavaScript concrete. Shared tokens made broad visual changes safer, while focused tests made layout and interaction changes easier to review.

Case study / Unix systems

Building a shell from tokens to processes

Minishell is a collaborative C project that recreates a focused subset of shell behavior through parsing, process management, file descriptors, environment state, and signal handling.

Role
Collaborative C development
Stack
C, Unix, Readline
Focus
Parsing and process management

Summary

A focused shell built in C

The project reads commands through Readline, records history, turns input into structured syntax, and executes commands with pipelines, redirections, heredocs, environment expansion, built-ins, and external programs.

Problem

Coordinate language rules with operating-system behavior

A shell has to interpret text and manage processes at the same time. Quote handling, variable expansion, redirections, and pipes all influence what should execute and which file descriptors each process should receive.

Implementation decisions

A staged route from text to execution

  • Lexical analysis preserves quote context for later expansion.
  • An abstract syntax tree represents commands, pipes, and redirections before execution.
  • Environment values and $? expand after parsing.
  • Pipelines use fork, execve, pipe, dup2, and waitpid.
  • Parent-process built-ins preserve shell state where needed.

Reliability and testing

Define the supported shell clearly

Syntax checks run before execution, cleanup is routed through token, AST, heredoc, environment, and descriptor helpers, and testing focuses on quoting, expansion, pipelines, redirection order, built-ins, exit statuses, heredocs, and signals.

Outcome and lessons

Parsing decisions become runtime behavior

Minishell connected data structures directly to operating-system behavior. Token types shaped the AST, and the AST shaped which processes and file descriptors existed at runtime.

Case study / Algorithms

Sorting integers through two constrained stacks

Push Swap validates integers, represents them as linked-list stacks, and prints a legal sequence of stack operations that places the values in ascending order.

Role
Algorithm design and C development
Stack
C, linked lists, Make
Focus
Ranking and operation planning

Summary

Sort by describing every allowed move

The program receives integers and may only manipulate two stacks with swap, push, rotate, and reverse-rotate operations. It prints the instructions that produce the sorted state, and a separate checker verifies the sequence.

Problem

Plan a short legal route through restricted operations

A general sorting algorithm cannot move values arbitrarily here. Every change must be expressed through valid stack operations, so data representation and movement strategy directly affect the generated instruction sequence.

Implementation decisions

Normalize first, then plan stack movement

  • Input validation rejects malformed, duplicate, and out-of-range integers.
  • Each linked-list node stores the original value and relative rank.
  • Small inputs use dedicated direct strategies.
  • Larger inputs move rank chunks between stacks before rebuilding stack A.
  • The checker independently applies instructions and reports OK or KO.

Validation and testing

Verify the result, not just the generator

Testing covers sorted input, duplicate and malformed values, small permutations, deterministic samples, unknown checker instructions, and generated sequences piped into the checker. The case study avoids benchmark or optimality claims without measured evidence.

Outcome and lessons

Algorithm quality becomes visible

Push Swap made every planning decision observable as a stream of legal operations. It reinforced that validation, representation, and independent verification are part of the algorithm's public contract.
